# テストしにくい部品にロジックを持たせない (Humble Object)

## 指摘すること

ブラウザ、DB、画面など、テストに本物の環境が要る部品が、文字列の解釈や変換などのロジックを持っていたら指摘する。ロジックは環境に依存しない部品 (純粋関数など) に切り出し、テストしにくい部品は独立した層に置いて、ロジック側からはインタフェース越しに使うよう求める。

あわせて、ロジック側の部品がテストしにくい部品に直接依存していて、そのテストに本物の環境が要るようになっていたら指摘する。

## 理由

ロジックを、環境なしで速くテストできるようにするため。テストしにくい部品は、テストしなくても困らないほど薄くする (Martin Fowler: "move as much as logic as possible out of the hard-to-test element")。

## 例

反している例: DB のリポジトリが、取得した行を料金の規則に従って計算してから返す。料金の計算をテストするのに DB が要る。

沿っている例: リポジトリは取得した行をそのまま返し、料金の計算は純粋関数にする。サービスはリポジトリのインタフェースに依存し、テストでは偽物を渡す。リポジトリ自体のテストは、クエリが実際のスキーマに合うことの確認だけにする。

## 出所

2026-11-15、ブラウザ自動化の Page Object にページの文字列の解釈を持たせ、ブラウザを使うテストで細かい条件まで確かめていた構成に対し、「infra 層はテストしない考え方がないか」と指摘された。さらに、ロジックを切り出したあとも、それを使う側が Page Object に直接依存していた案に対し、「infra みたいな層が無い」と指摘された。
