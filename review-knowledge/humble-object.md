# テストしにくい部品にロジックを持たせない (Humble Object)

## 指摘すること

ブラウザ、DB、画面など、テストに本物の環境が要る部品が、次のようなロジックを持っていたら指摘する。

- 取り出した文字列の解釈や変換
- 画面や応答の内容に応じた判断 (確認画面ならもう一度送信する、などの分岐)

ロジックは環境に依存しない部品 (純粋関数など) に切り出し、テストしにくい部品は独立した層に置いて、ロジック側からはインタフェース越しに使うよう求める。

あわせて、次の場合も指摘する。

- ロジック側の部品がテストしにくい部品に直接依存していて、そのテストに本物の環境が要るようになっている
- humble にした部品のテストがある。不要なので消し、動きは本物の環境で手で確かめるよう求める

## 理由

ロジックを、環境なしで速くテストできるようにするため。テストしにくい部品は、テストしなくても困らないほど薄くする (Martin Fowler: "move as much as logic as possible out of the hard-to-test element")。そのために薄くした部品なので、ユーザはテストを要らないと考えている。

## 例

反している例:

- DB のリポジトリが、取得した行を料金の規則に従って計算してから返す。料金の計算をテストするのに DB が要る。
- 画面を操作する部品が、送信後の画面を見て「確認画面なら承諾のボタンを押す」と判断している。
- 薄くしたリポジトリに、テスト用の DB を立ち上げて確かめるテストがある。

沿っている例: リポジトリは取得した行をそのまま返し、料金の計算は純粋関数にする。サービスはリポジトリのインタフェースに依存し、テストでは偽物を渡す。画面に応じた判断は、画面の文言を受け取るロジック側で行う。薄くした部品はテストせず、動きは本物の環境で手で確かめる。

## 出所

2026-11-15、ブラウザ自動化の Page Object にページの文字列の解釈を持たせ、ブラウザを使うテストで細かい条件まで確かめていた構成に対し、「infra 層はテストしない考え方がないか」と指摘された。さらに、ロジックを切り出したあとも、それを使う側が Page Object に直接依存していた案に対し、「infra みたいな層が無い」と指摘された。のちに、humble にした部品のテストを残していたことに対し、「humble object にしたからいらない」と指摘された。その際、humble な部品に入り込んでいた画面に応じた分岐も、ロジック側へ移した。
