# 独自のやり方より一般的なやり方に従う

## 指摘すること

次のような、そのプロジェクト独自のやり方を見つけたら指摘し、広く知られたやり方に従う形にするよう求める。

- 言語の書き方についての独自ルール。広く知られたスタイルガイド (TypeScript なら Google TypeScript Style Guide など) に従う形にする。コードが一般的なスタイルガイドから外れていて、その理由が書かれていない場合も指摘する。
- ツールの使い方や設定が、そのツールの普通の使い方と違い、使う人を驚かせるもの。標準のコマンドが本来の働きをしない設定 (引数なしの `tsc` で何も出力されない tsconfig など) や、一般的なビルドの手順を飛ばす構成 (TypeScript を tsc でビルドせず、型を取り除くだけで直接実行するなど) がこれに当たる。

## 理由

ユーザは、プロジェクト特有のやり方を決めるより、その言語やツールで一般的とされるやり方を好む。一般的なやり方なら、読む人も使う人も驚かない。きっかけの一つは、型を取り除くだけの直接実行では parameter property などの構文が使えず、一般的なスタイルガイドに沿った書き方ができなかったこと。

## 例

反している例:

- 文書に「ユーティリティは必ずアロー関数で定義する」のような、独自の書き方のルールがある。
- `tsconfig.json` が `noEmit` で型チェック専用になっていて、ビルドは別の設定ファイルで上書きして行う。`tsc` だけでは何も出力されない。
- `node src/main.ts` で直接実行し、tsconfig は `noEmit` と `erasableSyntaxOnly` で型チェック専用になっている。

沿っている例:

- 文書には「書き方は Google TypeScript Style Guide に従う」とだけ書き、個別のルールは持たない。
- `tsconfig.json` をビルド用にして `src/` を `dist/` に出力し、`tsc` だけでビルドする。テストの型チェックは、それを引き継いだ別の設定 (`test/tsconfig.json` など) で、出力せずに行う。

## 当てはまらない場合

- 層の分け方など、書き方ではなく設計についての決定。
- テストの書き方のように、ユーザ自身がルール化を求めたもの。

## 出所

2026-11-15、TypeScript のプロジェクトで、次の指摘を受けた。

- AI が文書に独自の書き方のルールを足していったのに対し、「プロジェクト特有の設計方針を決めるのではなく、一般的な美しい書き方がいい」と指摘された。
- 型を取り除くだけで直接実行する構成に対し、「tsc でビルドするようにしろ」と指示された。
- 型チェックの `tsc` で何も出力されないことに驚かれ、「tsconfig がおかしい」と指摘された。ユーザは、これらを「一般的なやり方に従ってほしい」というもっと大きな話の一例だと説明した。
