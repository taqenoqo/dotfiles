# DI のコンポジションルートは 1 か所で平らに組み立てる

## 指摘すること

DI で部品を組み立てる場所 (コンポジションルート) で、次のどれかを見つけたら指摘する。

- 組み立てが何か所にも分かれ、部品のつながりの全体を一目で読めない。資源の寿命を扱う関数 (「開いてコールバックに渡し、終わったら閉じる」形) のコールバックの中でしか部品を作れず、組み立てが内と外に散らばっている場合など。
- ルートの中で、port の実装をその場で書いている (インタフェースを満たすオブジェクトを直接書くなど)。

資源は「開いて返し、あとで閉じる」形にしてルートの冒頭で用意し、組み立ては 1 か所にまとめるよう求める。後始末は、言語の仕組み (`using` や try/finally など) で 1 か所にまとめる。

## 理由

コンポジションルートは部品のつながりを読む場所なので、読めば全体が分かる形であってほしい。コールバックの中に組み立てが散らばったり、実装が混ざったりすると、その役目を果たせない。

## 例

反している例: 接続を貸す `withConnection(async (db) => { ... })` のコールバックの中で一部の部品を作り、別の部品はその外で作り、さらにメールの送信の実装をルートの中にオブジェクトリテラルで書いている。

沿っている例: `await using db = await openConnection();` のように資源を先に用意し、`new App(new Repository(db), new Mailer(smtp), new Logger(console))` のように 1 か所で組み立てる。

## 出所

2026-11-15、use case をコンストラクタインジェクションに書き換えたあと、「コンポジションルートはどこ?シンプルに書かれてる?」と尋ねられた。組み立てがブラウザの寿命を扱うコールバックの中と外に分かれ、送信の実装もルートに直接書いていたので、資源を開いて返す形にして 1 か所にまとめるよう直させられた。
