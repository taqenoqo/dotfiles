# 依存はコンストラクタで注入する

## 指摘すること

use case やサービスのように、差し替えたい依存 (外部の仕組み、ユーザとのやり取りなど) を持つ処理が、依存を関数の引数やコールバックで受け取っていたら指摘し、依存をコンストラクタで受け取るクラスにするよう求める。承認や通知のような、ユーザとのやり取りをコールバックで渡している場合も、インタフェース (port) にしてコンストラクタで注入するよう求める。

## 理由

ユーザは、依存を引数で渡す関数のスタイルでは、Strategy パターンのような実装の差し替えがしにくいと考えている。依存をコンストラクタで受け取れば、組み立てる側で差し替えられ、呼び出すたびに依存を渡す必要もなくなる。

## 例

反している例: `sendReport(mailer, logger, reportId, { onSent, onError })` のように、依存と、処理ごとの値と、通知のコールバックをまとめて引数で受け取る関数。

沿っている例: `new SendReport(mailer, logger, notifier).execute(reportId)` のように、依存はコンストラクタで受け取り、実行時の引数は処理ごとの値だけにする。

## 当てはまらない場合

- 入力を受け取って値を返すだけの純粋関数 (形式の解釈や変換など)。差し替える依存を持たない。
- 呼び出す側ごとに中身が変わる処理の受け渡し (監視で見つけたものを、呼び出し側の処理に渡すなど)。依存ではなく処理ごとの引数として、実行時に渡してよい。今回、ユーザはこの形を受け入れた。

## 出所

2026-11-15、依存を引数で受け取る関数で use case を書いていたプロジェクトで、「コンストラクタインジェクションで DI っぽく書いてほしい」と指示され、承認や通知のコールバックも port にして注入する形にした。同じセッションの前半には、関数のスタイルで書く案を一度試していた。どのリポジトリにも当てはまる好みだと確認した。
