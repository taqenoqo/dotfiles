# my-review / my-review-learn スキル

## 設計方針

- `my-review-learn` がセッション中のユーザの指摘を知識として蓄え、`my-review` がその知識に照らしてレビューする。`home/.copilot/skills/` の `my-*-review` (観点が固定で、サブエージェントを束ねる) とは別物で、そちらには手を入れていない。
- 知識の実体は、リポジトリ直下の `review-knowledge/` に置く (`INDEX.md` と、1 知識 1 ファイルの詳細)。両スキルのディレクトリからは、相対シンボリックリンク `knowledge` で見せる。
    - スキルのディレクトリの中に実ディレクトリとして置かない。`install` が `home/` 配下の実ディレクトリをファイル単位のリンクに展開するので、学習で新しく作った詳細ファイルが `~` 側の実ファイルになり、`INDEX.md` への追記だけがリポジトリに届く。
    - スキル本文に「リンク先の実体を読み書きする」と書いて済ます案と、`install` にディレクトリ単位のリンクを足す案は採らなかった (ユーザの選択)。
- どちらもサブエージェントを使わない単一の `SKILL.md` にし、コマンドやツール名を書かない。Claude Code・Copilot CLI・Devin CLI・Codex など、どの環境でも同じ本文で通じるようにするため (ユーザの指定)。
- 知識は全リポジトリ共通のものだけにする。そのリポジトリ固有の決定は、従来どおりそのリポジトリの `AGENTS.md` に記録し、二重に記録しない。
- 学習は、ユーザが明示的に呼んだときだけ行い、書き込む前に案を見せて承認を取る。誤った知識は以後のレビュー全部に効くため。
- 知識には、プロジェクト固有の情報や社内の事情を絶対に書かせない。dotfiles は GitHub で公開しており、仕事のリポジトリでの指摘がそこに入るため (ユーザの指定)。学習スキルの本文でもこの理由を明示している。
- 学習の重複は、既存の知識との突き合わせに「変更なし」(既に含んでいるので案に出さない) という行き先を設けて防ぐ。同じセッションで学習を 2 回実行すると、1 回目に学習した指摘がもう一度拾われるため (ユーザの指摘)。「2 回目は前回以降の指摘だけを見る」という規則にはしない。同じセッションの再実行だけの特別扱いになり、会話が要約されると前回の範囲も分からなくなる。
    - ユーザが退けた候補は知識に残らず、突き合わせでは防げないので、拾わないものとして別に挙げている。
- 学習の案は、一覧 (1 件 1 行) → 相談 → 承認、の順に見せさせ、承認の前に詳細ファイルの全文を見せない。全文を見せていた版では、8 件・227 行が並び、ユーザは中身を確認せず承認もしなかった (ユーザの指摘:「認知的負荷が高いのは表示しないのと一緒」)。
    - 「公開されるので、漏れを止めるために承認前に全文を見せる」という理由で全文を残してはいけない。読まれない確認は確認にならず、相談と承認まで埋もれさせる。一度この理由で残し、差し戻された。
    - 中身の確認は、公開の前 (コミットと push の前) の差分に任せる。知識は git 管理で、取り消せなくなるのは push の時点。
    - 書き込み後に、エージェント自身に書かないと決めたものが残っていないかを見直させ、怪しい箇所だけをファイル名と行で報告させる。自己申告なので見落としはあり得る。
    - 相談は 1 件ずつ、問いを先頭に置かせ、選択肢を示して質問する機能があれば使わせる。「尋ねる」としか書いていなかった版では、質問機能が使われなかった。ツール名は書かない。
- 学習スキルはユーザが 1 回実行し、知識 8 件を書き込んだ (全文を見せる版)。見せ方を直した後の版と、レビュースキルは未実行。
