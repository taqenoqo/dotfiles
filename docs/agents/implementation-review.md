# implementation-review スキル

## 設計方針

- 問うのは「仕様と、実際に払ったコストが釣り合っているか」の一点。ズレは 2 方向ある。払いすぎ (過剰な仕様) なら撤回を提案し、払っていない (特定の入力にだけ通用する実装で仕様を黙って狭めた) なら一般に満たすかを問う。どちらも成果物はユーザへの問いであって、コードの改善ではない。
- 仕様の単位を「操作性の向上」のような抽象語に丸めさせてはいけない。抽象語にすると単位同士が区別できなくなり、「どれを落とせるか」の判断が原理的にできなくなる。書き直し前のスキルはこの一文のせいで機能していなかった。
- 代案を「同じ仕様を満たす別実装」としてサブエージェントに書かせる方式は廃止した。仕様を満たす限りどの代案も同じ複雑さを持つので、「仕様を削る」が探索空間に一度も入らない。
- 単純化を試した後は、振る舞いが変わっていないと言い切れるかを問わせる。判定は「差が小さいか」ではなく「差があるか」。「その入力は稀だから」で黙って適用させると、ユーザが選ぶ機会が消える。ここで「実際に動かして確かめる」と手段まで指定してはいけない。問うているのは静的な複雑さと仕様の釣り合いなのに、実行環境を組み立てる作業へ逸れ、コストの大半がそちらに消える。確信が持てないなら適用せず提案へ回せばよい。
- 空振りの回は一行で畳ませる。「検討した結果ちゃんと無かった」という説明も書かせない。毎編集後に走るので、空振りが長いと提案のある回が埋もれる。
- §1 で単位に出所 (指示 / 推測) を付けさせるとき、「推測由来は特に疑う価値がある」と書いてはいけない。裏返しに「指示された単位は疑わなくてよい」が伝わり、冒頭の宣言 (「あなたが求めたこの仕様、本当に必要ですか?」) と矛盾する。実測でも、指示由来のケースだけが全滅し、推測由来と「狭めた」ケースは通る、という分布になった。問う相手は指示由来の単位である。
- 検証済みの到達点 (Sonnet・リポジトリ外の清浄環境)。払いすぎ方向 (指示由来の過剰な仕様 / 推測由来の解釈) と払っていない方向 (直書き / メタデータでの代替) の 4 ケースが各 3/3、正例では一行で終える。バグ検出への脱線もゼロ。ただし「求めるものを既存の仕組みが既に提供している」の検出だけは Sonnet では届かず未解決で、そこは前項のコストの問題と表裏。
- 未検証なのは自発起動からの一連。評価はすべて「完成した実装を渡してスキルを実行しろ」と指示した条件で測っており、エージェントが自分で作業して自分の成果物を批判する経路は現行本文で確かめていない。`description` は変えていないので起動自体は変わらないはずだが、自分のコードに甘くなるかは別問題。
- 毎編集後に走る前提なので、周辺コードの調査を要求すると重すぎる。実測 (Sonnet, `claude -p`) では、空振りの回で +9 秒 / 出力トークン +29% / 課金差は誤差の範囲、提案が出る回で +85 秒 / 出力 +27% / +0.17 USD。空振りが安く済む形は保つこと。
- 「仕様を黙って狭めた」は一族として書く。直書きした名前やパスだけを例示すると、同じ一族の他の member (順に呼べば大丈夫、件数が少なければ大丈夫、この環境なら大丈夫) を拾えるかがモデルの一般化任せになる。実際、直書き以外の狭めを見つける回と見つけない回が混ざった。
- このスキルの本文は繊細なので、ユーザに頼まれない限り変えない。別の目的の問いを足す提案もしない。「既存の設計への継ぎ足しになっていないか」を 3 つ目の向きとして足したところ、ユーザに差し戻された (2026-11-15)。
