# スキルの評価

## 調査記録

- dotfiles 配下は asdf に python のバージョンが設定されておらず `python3` が起動しない。評価スクリプト等を回すときは `~/.asdf/installs/python/<ver>/bin/python3` を直接叩く。
- skill-creator の `eval-viewer/generate_review.py` はサンドボックス下ではソケット bind に失敗する (`PermissionError: [Errno 1]`)。`--static <path>` で単一 HTML を書き出す方式を使う。
- skill-creator の `aggregate_benchmark` は `eval-*/<config>/run-*/grading.json` という階層と、grading.json の `summary` キーを要求する。この形になっていないと警告を出さずに全項目 0% で集計される。
- サブエージェントの完了報告は成果物の実在確認とセットで扱う。「response.md を保存しました」と報告しながらファイルが存在しなかった実例がある。
- スキルの評価は同一モデルで新旧を走らせないと比較にならない。モデルを変えると絶対品質が動くため、退行がスキル本文由来かモデル由来か切り分けられなくなる。
- 「求めるものを既存の仕組みが既に提供している」の検出は難しい。Opus は自力で気づいたが、Sonnet は清浄な環境では拾えなかった。一度は §2 への追記で埋まったように見えたが、それは `AGENTS.md` 自体が答えを含んでいたためで、汚染を除くと再現しない。周辺のファイルを実際に見に行かせるところまで本文で指示しないと、モデルは知識だけで答えて終わる。
- スキルの自発起動には `~/.claude/skills/` への設置が要る。`install` 前は `home/.claude/skills/` が「`home/` 配下を触るときに適用」というスコープ付きで登録されるため、それ以外の場所で作業するサブエージェントは対象外として起動しない。設置と再起動を済ませた状態では、スキルに一切言及しない依頼から Sonnet が 2/2 で implementation-review を自発起動した。起動の可否はスキル本文ではなく可用性の問題だった。
- スキル一覧 (name・description・スコープ) とグローバル指示は、セッション開始時のスナップショットで固定される。`install` や `AGENTS.md` の編集をセッション中に行っても、そのセッションのサブエージェントには反映されない。起動を検証するときはセッションを開き直すこと。
- Task ツールのサブエージェントは、作業ディレクトリがどこであってもセッションの cwd に基づいて `CLAUDE.md` → `AGENTS.md` を読み込む。つまりこのリポジトリで評価を回すと、`AGENTS.md` の内容がすべてヒントとして配られる。実際、評価 5 件のうち 2 件が `AGENTS.md` の記述に依存して通っており、除去すると落ちた。テスト直前に消しても前項のスナップショットで間に合わない。
- 汚染のないスキル評価は、リポジトリ外のディレクトリを cwd にして `claude -p` を起動する。スキル本体と入力もそこへコピーし、リポジトリを一切参照させない。この方式ではプロジェクトの `AGENTS.md` も memory の内容も注入されず、グローバル指示だけが残る (実運用と同じ条件)。プロンプトは可変長フラグ (`--allowedTools` など) に飲まれないよう stdin で渡す。
- サブエージェントのトランスクリプトに残るのは会話 (user / assistant / attachment) だけで、システム注入は記録されない。`system-reminder` の出現数すら 0 になる。注入の有無を調べるには、エージェント自身にコンテキストを引用させること。ファイル読み込みの有無は tool 呼び出しとして残るので grep で追える。
- `claude -p` をサンドボックス内から起動すると、子プロセスの Bash が `EPERM` で塞がれる。実測を伴う評価は成立しないので、サンドボックスを外して起動すること。
- サブエージェントが実際にどのモデルで走ったかは、タスクのトランスクリプト (`<session>/tasks/<agentId>.output`) の `"model"` フィールドで確認できる。`grep -o '"model":"[^"]*"' <file> | sort -u` で足りる (トランスクリプト全体を読むとコンテキストが溢れるので grep で絞ること)。上限到達時に現れる `"model":"<synthetic>"` はハーネスのエラーメッセージで、別モデルでの実行ではない。
- 同じスキル・同じ入力でも、提案を出す回と「該当なし」で畳む回が混ざる (実測で 3 回中 1 回が空振り)。1 回の空振りを見てスキル本文の欠陥と診断してはいけない。原因を本文に帰属させる前に、同じ条件で複数回走らせて再現するか確かめること。実際、空振りを根拠に §4 を書き換えたが、書き換え前のスキルが同じ入力で提案を出し、修正は無意味だったと判明した。
- 評価ケースに見つかる欠陥が 2 つ以上あると、劇的な方 (データ消失など) に注意が集中し、もう一方は誰も報告しない。特定の指摘を測りたいケースは、その指摘以外に見つかるものが無い入力にすること。欠陥が 2 つあるケースでは 3 体全員が同じ片方だけを報告し、狙っていた指摘は 1 体も出さなかった。欠陥を 1 つに絞ったケースに作り直すと、3 体全員が同じ 1 点に収束した。
- `claude -p --output-format json` の `usage` と `modelUsage` は累計で、欠測はない。ただし総量の 98% が `cache_read_input_tokens` で、その量はターン数で決まる。単価は出力の約 1/10 なので、出力トークンと足した「総トークン」には意味がない。ターン数が 1 減っただけで「スキルを使う方が安い」という辻褄の合わない結果になる。比べるなら出力トークンと `total_cost_usd` を分けて見ること。
- LLM に単純化案を検証させると、その案が拠り所にしている当の仕組みを固定してから測ることがある (時刻の一意性に頼る案を、時刻を固定した状態でテストするなど)。それでは必ず失敗するので、案の前提を潰さない測り方になっているかを確かめること。
