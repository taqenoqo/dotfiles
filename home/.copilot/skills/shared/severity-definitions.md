# 重大度定義

レビュー指摘の重大度を以下の5段階で評価してください。

## `must`

- **定義:** 客観的な誤り。「このコードは作者のミスである」とコードを見ただけで断定でき、「あえてこうしている」という反論が成り立たないもの。
- **具体例:** 未処理の null 参照、認証バイパス、空ファイルの混入、使われていない import の大量追加、明らかな typo によるバグ、ログに秘密情報が出力される

## `imo`

- **定義:** 設計上の改善提案。作者が「あえてこうしている」と反論すれば議論になり得る。ただし、**プロジェクトの既存多数派パターンから逸脱している**場合はこの重大度。
- **具体例:** 既存の多数派が Repository パターンを使っているのに直接 DB アクセスしている、長すぎるメソッドの分割提案

## `nits`

- **定義:** 正誤は明白だが、修正しなくても実害が少ないもの。
- **具体例:** typo、コメントの誤字、軽微なフォーマット不統一

## `ask`

- **定義:** 判断に必要な情報が不足しており、作者に質問したいもの。
- **具体例:** 「この設計は意図的ですか？〇〇のためにあえてこうしていますか？」

## `reject`

- **定義:** レビューコメントとして出すほどではないもの。指摘する価値がない。
- **具体例:** 下記の reject 基準に該当する場合

## reject にすべきケース

以下に当てはまる場合は、たとえ理想論として正しくても `reject` としてください：

1. **既存多数派パターンの踏襲:** 既存コードの多数（50%以上）が同じことをしている場合、このPRだけを指摘するのは不公平。プロジェクト全体の負債であり、このPRのレビューコメントではない。
2. **理想論 vs 現実:** アーキテクチャ本に書いてある理想と異なるが、このプロジェクトの文脈では合理的な選択である場合。
3. **コストに見合わない改善:** リファクタリングの効果が小さく、変更コストに見合わない場合。

## 判定前の必須チェック

重大度を決定する前に、以下を必ず確認してください：

1. **既存パターン調査:** この指摘の対象と同じことをしている既存コードが何箇所あるか？ 多数派と同じなら `reject`。
2. **新規導入かどうか:** この問題はPRの差分で新たに導入されたか？ それとも既存パターンの踏襲か？
3. **前提の検証:** 「〇〇が標準パターン」と思い込んでいないか？ 実際にコードベースを grep して何%がそのパターンに従っているか確認したか？
