# 重大度定義

レビュー指摘の重大度を以下の6段階で評価してください。

## `must`

- **定義:** 客観的な誤り。「このコードは作者のミスである」とコードを見ただけで断定でき、「あえてこうしている」という反論が成り立たないもの。
- **具体例:** 未処理の null 参照、認証バイパス、空ファイルの混入、使われていない import の大量追加、明らかな typo によるバグ、ログに秘密情報が出力される、プロジェクト共通のロガーを使わず console.log を使っている
- **must にならないもの:** 設計書との不整合（設計書が古い・使い捨ての可能性がある）、既存負債の踏襲（このPRで直す義務はない）、「理想的にはこうすべき」という改善案

## `imo`

- **定義:** 設計上の改善提案。作者が「あえてこうしている」「スコープ外」と反論すれば議論になり得る。プロジェクトの既存多数派パターンから逸脱しているなどもこの重大度。
- **具体例:** 既存の多数派が Repository パターンを使っているのに直接 DB アクセスしている、長すぎるメソッドの分割提案、同じ PR 内で新旧パターンが混在している

## `next`

- **定義:** このPRでの修正は求めないが、プロジェクトの技術的負債として認識を共有したいもの。既存多数派パターンの踏襲であっても、明らかに問題がある場合にこのラベルで知識を残す。
- **具体例:** 「既存コードの多くが同じ問題を抱えていますが、次に触る機会があれば改善を検討してください」「このパターンはプロジェクト全体の負債です。今回は既存踏襲で問題ありませんが、将来的には〇〇が望ましいです」
- **imo との違い:** `imo` はこのPRでの対応を期待する。`next` はこのPRでは不要だが、次の機会での改善を提案する。

## `nits`

- **定義:** 正誤は明白だが、修正しなくても実害が少ないもの。
- **具体例:** typo、コメントの誤字、軽微なフォーマット不統一

## `ask`

- **定義:** 判断に必要な情報が不足しており、作者に質問したいもの。
- **具体例:** 「この設計は意図的ですか？〇〇のためにあえてこうしていますか？」

## `reject`

- **定義:** レビューコメントとして出すほどではないもの。指摘する価値がない。
- **具体例:** 下記の reject 基準に該当する場合

## reject にすべきケース

以下に当てはまる場合は、たとえ理想論として正しくても `reject` としてください：

1. **既存多数派パターンの踏襲かつ問題が軽微:** 既存コードの多数が同じことをしていて、かつ実害も小さい場合。（実害が大きい場合は `next` を検討）
2. **理想論 vs 現実:** アーキテクチャ本に書いてある理想と異なるが、このプロジェクトの文脈では合理的な選択である場合。
3. **コストに見合わない改善:** リファクタリングの効果が小さく、変更コストに見合わない場合。

## 判定前の必須チェック

重大度を決定する前に、以下を必ず確認してください：

1. **既存パターン調査:** この指摘の対象と同じことをしている既存コードが何箇所あるか？ 多数派と同じなら `next`（問題が大きい場合）か `reject`（問題が軽微な場合）。
2. **新規導入かどうか:** この問題はPRの差分で新たに導入されたか？ それとも既存パターンの踏襲か？
3. **前提の検証:** 「〇〇が標準パターン」と思い込んでいないか？ 実際にコードベースを grep して何%がそのパターンに従っているか確認したか？
4. **反論テスト:** `must` を付けようとしているなら、作者が「デプロイ都合」「スコープ外」「設計書が古い」等と反論したとき、それで議論が終わってしまうか？ 終わるなら `imo` に下げる。
5. **設計書の信頼性:** 設計書・spec を根拠にする場合、それが最新の実装と一致しているか？ AI 向けの使い捨て設計書（spec-driven development のドキュメント等）を権威として扱っていないか？
