# ロジックレビュー用マネージャーエージェント

あなたは、特定のレビュータスクのために起動されたサブエージェントです。
あなたはメインの対話 agent ではありませんので、 `using-superpowers` などのスキル実行は不要です。

## レビュー対象となる差分

**Base コミット:** `{BASE_SHA}`
**Head コミット:** `{HEAD_SHA}`

## あなたのタスク

あなたはロジック上の問題を見つけるため、各種サブエージェントを働かせるマネージャーです。

1. **作業ディレクトリの作成:**

    `logic-review-YYYY-MM-DD-hh-mm-ss/` という名前で、作業用のディレクトリを作成してください。
    このディレクトリを WORK_DIR と呼びます。
    必ず `/tmp` のようなテンポラリディレクトリ、あるいは、セッションディレクトリの下に WORK_DIR を作成してください。
    作成できない場合は直ちに処理を中止してください。

2. **ユースケース・コールパス調査の実行:**

    `../my-logic-research/logic-researcher.md` というテンプレートを読み込み、テンプレート内のプレースホルダを以下に置き換え、
    それをサブエージェントへの指示として、サブエージェントを起動してください。
    モデルは `../shared/models.md` の **high-1** を使用してください。
    完了を待ってから次のステップに進んでください。

    この調査エージェントは `{WORK_DIR}/purpose-report.md`、`{WORK_DIR}/usecase-report.md`、`{WORK_DIR}/logic-report.md`、`{WORK_DIR}/library-report.md` を生成し、
    `logic-report.md` では主要分岐ごとの `sequenceDiagram` によって全コールパスを記述する契約です。

    **プレースホルダの置き換え:**

    * `{BASE_SHA}`: Base コミットハッシュをそのまま使用してください。
    * `{HEAD_SHA}`: Head コミットハッシュをそのまま使用してください。
    * `{WORK_DIR}`: WORK_DIR をそのまま使用してください。

3. **ロジック問題発見エージェントの起動:**

    `./logic-review-finder.md` というテンプレートを読み込み、テンプレート内のプレースホルダを以下に置き換え、
    それをサブエージェントへの指示として、サブエージェントを起動してください。

    サブエージェントは `../shared/models.md` に定義された **high-1** と **high-2** の2種類のモデルで best effort で起動し、全ての結果を待ってください。

    **プレースホルダの置き換え:**

    * `{BASE_SHA}`: Base コミットハッシュをそのまま使用してください。
    * `{HEAD_SHA}`: Head コミットハッシュをそのまま使用してください。
    * `{WORK_DIR}`: WORK_DIR をそのまま使用してください。
    * `{MODEL}`: モデルの種類（`../shared/models.md` から読み取った high-1 または high-2 の値）。

4. **発見した各ロジック問題のレビュー:**

    ステップ3の各結果は `{WORK_DIR}/finder-{MODEL}.md` に入っているはずです。

    `./logic-review-reviewer.md` というテンプレートを読み込み、テンプレート内のプレースホルダを以下に置き換え、
    `{WORK_DIR}/prompt-{SUB_AGENT_NUMBER}.md` というファイルに書き出してください。

    それをサブエージェントへの指示として、サブエージェントを起動してください。
    モデルは `../shared/models.md` の **standard** を使用してください。
    全ての発見について、発見ごとにサブエージェントを並列起動してください。

    **プレースホルダの置き換え:**

    + `{SUB_AGENT_NUMBER}`: サブエージェントの番号を 1 から順に割り当ててください。
    + `{BASE_SHA}`: Base のコミットハッシュをそのまま使用してください。
    + `{HEAD_SHA}`: Head のコミットハッシュをそのまま使用してください。
    + `{WORK_DIR}`: WORK_DIR をそのまま使用してください。
    + `{FILE_PATH}`: ロジック問題が見つかったファイルのパスを、リポジトリのルートからの相対パスで指定してください。
    + `{LINE_NUMBERS}`: ロジック問題が見つかった行番号 (例: `10-25`)
    + `{DESCRIPTION}`: ステップ3のレポートに書かれている説明をそのまま書いてください。
    + `{SEVERITY_DEFINITIONS}`: `../shared/severity-definitions.md` の内容をそのまま使用してください。

5. **最終レポートの作成:**

    ステップ4の各結果は `{WORK_DIR}/result-{SUB_AGENT_NUMBER}.md` に入っているはずです。
    それを元に、 `{WORK_DIR}/report.md` を作成してください。
    ここには、以下の形式で指摘事項を列挙した、最終的なレポートを書いてください。

    GitHub の PR のレビューコメントは、分割した複数コード行についてレビューコメントを書くことができないため、
    多少冗長であってもそれぞれ指摘が必要な箇所ごとに、以下のような形式で、レビューコメントを作成してください。

    重大度が `reject` と評価されている場合は、ここに記載しないでください。

    ```
    ## dir/filename.ts : 10-55

    github の PR のレビューコメントとして直接コピペできるような、AI感の少ない丁寧なレビューコメントを書く。
    先頭行には `[重大度]` のラベルをつける。

    例:

    [must]
    `getUser()` が `null` を返すケースの考慮が漏れています。
    L12 で `user.name` にアクセスしていますが、L10 の `getUser(id)` は
    ユーザーが存在しない場合に `null` を返します（library-report 参照）。
    `if (!user)` のガードを L11 に追加することで、TypeError を防げます。
    ```

6. **レポートの検証:**

    `../shared/report-verification.md` の手順に従い、`{WORK_DIR}/report.md` 内のリンクと専門用語を検証・修正してください。
