担当: レポートのセクション 3「アーキテクチャ・パターン」(report-format.md 参照)。

## 目的

後段のリファクタリング・レビューのエージェントが「このリポジトリの設計意図」を前提にできるよう、
採用されているアーキテクチャ・デザインパターンと依存の規則を、根拠付きで記録する。

## 内容

* **モジュール間依存:** 依存一覧(deps.tsv)をディレクトリ(モジュール)単位に丸め、mermaid の依存グラフで書く
    + ノードはディレクトリ単位に丸める(ファイル単位にしない)
* **依存方向の規則:** グラフから観測される依存の向きの規則を導く
    + 例: 「`ui/` → `core/` の依存が 24 件、逆向きは 0 件。core は ui に依存しない規則があるとみられる」
    + 規則に対する例外(逆向き依存)があれば、件数と具体パスを列挙する
* **採用パターン:** アーキテクチャパターン(レイヤード、hexagonal、MVC 等)・デザインパターン(Repository、DI、Factory 等)のうち、構造から観測できるものを列挙する
    + 各パターンに、それを構成する具体的なディレクトリ・クラス群を必ず添える
    + DIP の適用(インターフェースによる依存の逆転)に注意する
* **循環・逸脱:** 依存一覧から見つけた循環と、規則からの逸脱を列挙する

## ルール

* **証拠のないパターン名を書かない。** 構成するディレクトリ・クラス群を列挙できないパターンは、書かずに「未確定・質問」に送る。
* パターンや規則の「意図」(なぜそうしたか)は推測しない。意図の確認は「未確定・質問」に送る。
* 依存一覧は抽出時の解決に依存し取りこぼしがあり得るため、依存の件数は「観測できた範囲」として書き、網羅を断定しない。
