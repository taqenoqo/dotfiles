# repo-report 成果物契約

`.repo-report/gen.md` の形式の定義。
このファイルは my-repo-report スキルの各エージェントと、成果物を読む他スキル(my-pr-review 等)の間の契約であり、セクション構成を勝手に変えないこと。

## ファイル構成

- `.repo-report/gen.md` — 生成レポート。再生成のたびに全体が上書きされる
- `.repo-report/notes.md` — 人間が書く注記(慣習の意図・歴史的経緯など)。スキルは読むだけで、絶対に編集しない

## frontmatter

```yaml
---
generated_at: <HEAD の SHA>
date: <YYYY-MM-DD>
---
```

## セクション構成(固定順・見出しもこの通りにする)

1. `## 概要` — リポジトリが何か、1 段落
2. `## ディレクトリ構成と責務` — トップレベルディレクトリの表(パス / 責務 / 規模)
3. `## アーキテクチャ・パターン` — モジュール依存グラフ(mermaid)、依存方向の規則、採用されているアーキテクチャ・デザインパターンとその根拠、循環・逸脱の列挙
4. `## 公開 API 面` — 外部に公開している面(export / HTTP / CLI / 設定形式等)の説明と、種類ごとの目録(辞書順の表)。後段のレビューが破壊的変更の検出に diff で使う
5. `## 共有ユーティリティ目録` — 再発明防止用の索引。表(名前 / 場所 / 用途 1 行)
6. `## 命名・コード慣習` — 命名規則、エラー処理、テスト等の慣習。観測数付き
7. `## エントリポイント・ビルド・テスト` — 起動点と主要コマンド
8. `## 規模メトリクス・ホットスポット` — 集計スクリプトの出力そのまま(関数長、クラス規模、public/private、変更ホットスポット)
9. `## 人間への質問` — 生成時に確信が持てなかったこと。回答は notes.md に書いてもらう

## 記述の規律

- 断定には根拠を添える。例: 「42 ファイル中 38 で snake_case」
- リポジトリに実在しないファイル名・シンボル名を書かない
- 文は宣言的な短文。リストは意味的な順序がなければ辞書順にソート(再生成 diff を読みやすく保つため)
- 規模を示す数値(行数・ファイル数の合計等)は概数に丸めてよい。観測数(「42 ファイル中 38 で」等)は正確に数える
- アーキテクチャ・デザインパターンの認定には、それを構成するディレクトリ・クラス群の列挙という構造的証拠を必須とする。証拠を挙げられないパターン名は書かず「人間への質問」に送る
- セクション 8 の本文は集計スクリプトの出力をそのまま用いる。手で数え直さない・改変しない
- 確信が持てないことは本文で断定せず「人間への質問」に送る

## 修正の還流先

- 内容の誤り・補足したい意図や経緯 → `notes.md` に書く(gen.md への直接修正は次の再生成で消える)
