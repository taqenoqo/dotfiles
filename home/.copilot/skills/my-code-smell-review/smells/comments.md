# Comments（コメント）

<https://refactoring.guru/smells/comments>

## 兆候と症状

メソッドの中が説明コメントだらけになっている。

## 原因

コメントはたいてい善意から書かれる。書き手が「このコードは直感的でも明快でもない」と気づいたとき、その補足としてコメントを足すからだ。しかしそうしたコメントは、改善できるはずの怪しいコードのにおいを、消臭剤でごまかしているだけのことが多い。

> 最良のコメントは、メソッドやクラスに付けられた良い名前である。

コメントがないと理解できないコード片があるなら、コメントで補うのではなく、コメント不要で読める構造に変えられないか考えるべきである。

## 治療法

- 複雑な式を説明するコメントなら、[Extract Variable](https://refactoring.guru/extract-variable) で理解しやすい部分式に分ける
- あるコードのまとまりを説明するコメントなら、その部分を [Extract Method](https://refactoring.guru/extract-method) で別メソッドに切り出す。新しいメソッド名は、コメント文そのものが候補になることが多い
- すでにメソッドを切り出しているのに、その役割を説明するコメントがまだ必要なら、[Rename Method](https://refactoring.guru/rename-method) で自己説明的な名前に変える
- システムが正しく動くために必要な状態のルールを明示したいなら、[Introduce Assertion](https://refactoring.guru/introduce-assertion) を使う

## 効果

コードがより直感的でわかりやすくなる。

## 無視してよい場合

コメントが役立つ場面もある。

- その実装にした **理由（why）** を説明したいとき
- アルゴリズムを単純化するために手を尽くしてもなお、複雑なアルゴリズムの説明が必要なとき
