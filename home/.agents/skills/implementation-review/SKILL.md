# 実装後の見直し

エージェントに対する実装要求などの指示は、具体的な実装後のコードを知る前の人間の指示であり、実装を見た後は考えが変わる可能性がある。
このスキルは、実装後のコードの規模や複雑さが、提供したかったと思われる価値に見合っているかを検証し、簡易修正し、価値に対する複雑さの不釣り合いを報告する。

機能実現上は仕方なかったものの、コードとしては不格好な箇所を検出し、
可能であればよりシンプルな形に修正し、それでも不格好な部分が残る場合はそれを呼び出し元に報告する。

## 1. 価値の列挙

今回の実装にどのような機能要件上の「価値」があるかを記述する。

「価値」とは命令された要件や指示内容ではない。
その機能や問題解決によってユーザが得られる利点のこと。
与えられていない場合は推測する必要がある。
価値として「機能」や「実現できること」は一切書いてはならない。
「〇〇性の向上」などだけを書くこと。

* 悪い例: 「見やすいボタンが表示できる」
* 良い例: 「操作性の向上」

## 2. 臭いの列挙

文章やプログラム等の実装箇所のうち、以下の「臭い」リストに少しでも該当する箇所をできるだけ多く列挙する。
また、その箇所がどの価値に属するかも併せて記述する。

* 「特殊技術」: 今回使われている言語・ライブラリ等の固有技術を知らない一般的プログラマが、他の言語の経験からの類推でそのコードの意味を理解できない箇所。その技術固有の仕様を調べなければ理解できない箇所。
* 「応急処置コード」: 与えられた具体的な要件や特定の問題解決に特化してしまっている箇所。特に、同種のものが潜在的に多数ある中で一部のみを特別扱いしてしまっている箇所。

## 3. 臭いの評価

上で列挙した各「臭い」ごとに、「検証」か「放置」かをタグ付けした表を出力する。
タグ付けの根拠として、以下リストに適合するか検証し、1つでも適合したら「検証」とする。1つも適合せず「放置」する場合は以下の全てについてそれぞれと一致しないことを説明する。

* 「価値」の大きさに対する「臭い」の強さ。あなたがこの要求考えたとして、この実装になってしまうことをしていたら要求事項を変えた場合は「検証」タグを付ける。
* 実装を真似したコードが100箇所に増えた未来を仮定し、その未来において可読性が低い、または、場当たり的コードだらけになる場合は「検証」タグを付ける。
    + 仮定の話なので現状の話は正当化の根拠にならない。この時点で YAGNI は想定しない。

## 4. 再実装

「検証」とタグ付けされた箇所について、現在案から独立した代案コードをサブエージェントに実装させる。
サブエージェントは2つ走らせる。

* 現在の実装方針や要件に引っ張られない多用な実装をさせるため、サブエージェントにはあなたの実装したコードだけを渡し、機能要件や実装方針を一切与えない。
* 現在の環境の汚染を避けるため、サブエージェントにはあなたの実装したコードのsnapshotを渡す。サブエージェントにはその範囲外の書き換えを禁止する。
* 現在案と重複した実装を避けるため、どのような「臭い」が問題になっているか、上記の「臭いリスト」の該当文を渡し、そしてそれを避けて実装するよう指示する。

## 5. 選択

今回のあなたの実装と、サブエージェントが実装した代案を比較する。
良い方の実装例を採用する。その際、理由も出力する。

## 6. 結果出力

サブエージェントの代案を棄却し、現実装を維持したということは、臭いが残っていることを意味し、具体的な実装を得たユーザがあなたに与えた命令を考え直す可能性があることを意味する。
そのため、サブエージェントの代案を棄却した場合、例外なく必ず呼び出し元にそのことを詳細に報告しなければならない。
出力にはその「臭い」がどの「価値」由来なのかを明示する。
