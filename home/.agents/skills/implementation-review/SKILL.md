# 実装後の仕様見直し

人間は、実装を見る前に仕様を決めている。だから「その一言がこれだけの複雑さを買っていた」と知る機会が無いまま、
コストを承知しない仕様が確定してしまう。実装を終えたあなたは、その値札を唯一知っている立場にいる。

このスキルの成果物は、コードの改善ではなく **ユーザへの問い** である。

> 実装してみたらこうなりました。あなたが求めたこの仕様、本当に必要ですか?

**これはコードレビューではない。** コードの品質や設計の良し悪しを論じる場ではない。
問うのは「この要求は、判明したコストを払ってでも欲しいものか」の一点だけ。
コードの直し方の話に逸れたら、それは別の作業に迷い込んでいる。

## 1. 仕様を、落とせる単位に分ける

今回の編集で満たした要求を並べる。単位の切り方は「これだけ撤回しても、残りは成立するか」が YES になる最小の塊。

**具体的な言葉で書く。**「操作性の向上」「保守性の改善」のような抽象語に丸めてはいけない。
抽象語にすると単位同士が区別できなくなり、「どれを落とせるか」という後続の判断が原理的にできなくなる。
ユーザが口にした言葉、あるいはコードが実際にやっていることを、そのまま書く。

各単位に出所を付ける。

- **指示** — ユーザが明示的に求めた
- **推測** — あなたが「あった方がよかろう」と補った

推測由来の単位は、ユーザがコストを承知で買ったわけではないので、特に疑う価値がある。

あわせて、実装が各単位を **どの範囲で** 満たしているかを書く。
特定の名前・特定のパス・特定の値でだけ成立する実装は、その単位を満たしたのではなく、黙って狭めている。
狭めたことを黙っていると、ユーザは満たされたと思い込んだまま確定してしまう。

例（tmux のキーバインド追加）:

- A. `prefix+Enter` で左60%の主ペイン + 右40%の縦積みに整形する（指示）
- B. そのとき、カーソルのあるペインを主ペインの位置へ入れ替える（指示）

## 2. 各単位に、コードを帰属させる

単位ごとに「これを仕様から外したら、コードはどうなるか」を **実際に書き下す**。
頭の中で見積もらない。書いてみるまで、どれだけ消えるかは自分でも分かっていない。

消えるものを具体的に挙げる。

- 行数
- 構文 — 条件分岐、状態、ループ、早期リターン、例外処理
- その言語やツールに固有の機能 — 一般的なプログラマが他言語からの類推で読めず、仕様を調べないと意味が取れないもの
- 失敗モード — 分岐漏れ、環境依存、順序依存、競合
- テスト、設定、ドキュメント

あわせて、その単位を自分で書かずに済ませる手段が既にないかを確かめる。
言語やツールの標準機能、導入済みのライブラリ、同じリポジトリの既存コードが同じことを提供しているなら、
帰属したコストは全額が無駄になる。しかも自前の実装が既存のものを黙って上書きし、機能を減らしていることがある。

例:

- A を外す → この機能自体が消える。A は目的そのものなので撤回対象にならない
- B を外す → `if-shell` による条件分岐が丸ごと消え、レイアウト指定の2行だけになる

文章が対象なら、消える段落、条件付きの但し書き、読み手に前提知識を要求する箇所を挙げる。

## 3. 仕様を保ったままの単純化を先に試す

複雑さは、仕様のせいではなく実装の下手さのせいかもしれない。
仕様を全部満たしたまま素直に書けないか、実際に書き直してみる。
それで複雑さが消えるなら仕様の問題ではないので、直して終わりにする。ユーザに聞く必要はない。

ここを飛ばすと、自分の実装の拙さの請求書をユーザに回すことになる。
ユーザは判断材料を持っていないので、その問いには答えられない。

書き直したら、振る舞いが変わっていないかを、実際に入力を変えて確かめる。
**差が小さいかどうかではなく、差があるかどうかで判定する。**「その入力は稀だから」は理由にならない。
振る舞いが変わるなら、それは単純化ではなく仕様の撤回である。勝手に適用せず、4 へ回して提案にする。

## 4. 不釣り合いを判定する

残った複雑さについて、単位ごとに「恩恵」と「帰属したコスト」を並べる。
以下のどれかに当たるものだけを、再検討の提案対象にする。

- 恩恵は「あると少し楽」程度なのに、コストが構造を変えている（分岐が増えた、状態を持った、処理順に依存するようになった）
- その単位のためだけに、他の単位が使っていない特殊な機能や技法を持ち込んだ
- **あなたがこの仕様を出す側だったとして、このコードになると知っていたら、その一言を言わなかった**
- その単位を外すと、コードが「読めば分かる」水準まで落ちる
- その単位が求めるものを、既存の仕組みが既に提供している（コストは全額、恩恵はゼロ）
- その単位を、特定の入力にだけ通用する形で片付けた（同種のものが他にもあるのに、一部だけを名指しで特別扱いした）

逆に、以下は通す。撤回を提案しても意味がないため。

- 目的そのものである単位（外すと機能が消える）
- 複雑さが単位に帰属せず、扱う問題そのものに由来するもの

当たらないものは黙って通す。全部を疑うと、本当に問うべき回が雑音に埋もれて届かなくなる。

## 5. 提案する

読み手が最初に知りたいのは「何を聞かれているか」であって、その根拠ではない。
提案が2件以上あるときは、本文の前に一覧を置く。

```
## 仕様の再検討の提案（<件数>件）

1. <対象の仕様> — 外すと<何がどれだけ消えるか>
2. <対象の仕様> — 外すと<何がどれだけ消えるか>
```

続けて、該当した単位ごとに以下を出力する。コードは要約せず現物を貼る。
値札を見せるのが目的なので、抽象的な説明では用を成さない。
「消えるもの」に並べる**証拠**は、判断を左右するものだけに絞る。
手元にある実測結果を全部貼ると、肝心の問いがその中に埋もれる。
ただし絞るのは証拠であって、提案の件数ではない。
恩恵が小さいと感じた単位ほど外せる可能性が高いので、小さいことを理由に黙ってはいけない。

```
## 仕様の再検討の提案

**対象の仕様**: <落とせる単位を、具体的な言葉で。出所（指示 / 推測）も添える>

**実装したらこうなりました**:
<現物のコード。該当箇所のみ>

**この仕様を外すとこうなります**:
<現物のコード>

**消えるもの**: <行数・構文・特殊機能・失敗モード>

**この仕様の恩恵**: <外すと失われるもの>

この仕様は本当に必要ですか?
```

仕様を狭めて済ませた単位では、「この仕様を外すとこうなります」を
「この仕様を一般に満たすとこうなります」に読み替える。
問いは「この仕様は本当に全部必要ですか、それとも今の範囲で十分ですか?」になる。

提案しただけで仕様を変更してはならない。撤回するかどうかはユーザの決定であって、あなたの決定ではない。
返事を待たずにコードから消すと、ユーザは選ぶ機会を奪われる。

この提案は、今回の作業のユーザ向け最終回答にそのまま含める。
作業報告の中に要約して埋めると、ユーザは値札を見ないまま仕様を追認することになる。

## 6. 該当が無ければ一行で終える

これが最も多い結末である。以下だけを書いて終わる。

```
仕様の再検討を要する箇所はありません。
```

この一行だけを書く。検討した単位の一覧も、判定の根拠も、
**「検討した結果ちゃんと無かった」という説明も** 書かない。
毎回の編集後に走るスキルなので、空振りの回を短く畳むことが、提案のある回を目立たせる。
