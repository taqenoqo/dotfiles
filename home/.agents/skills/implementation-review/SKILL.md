# 実装後の見直し

基本的に実装は1パターンだけで完了してはならない。何かしらの編集作業をしたあとは以下の手順を必ず毎回実行すること。これは「臭い」箇所に限定して、代案と比較検証する重要手順であり、**全ステップ省略禁止**。

1. 文章やプログラム等の実装完了時、実装した部分から以下の「臭い」リストに **少しでも** 該当する可能性がある箇所をできるだけ多く列挙する。
    + 今回使われている言語・ライブラリ等の固有技術を知らない一般的プログラマが、他の言語の経験からの類推でコードの意味を理解できない箇所。その技術固有の仕様を調べなければ理解できない箇所。
    + 与えられた具体的な要件や特定の問題解決に特化してしまっている箇所。特に、同種のものが潜在的に多数ある中で一部のみを特別扱いしてしまっている箇所。
    + 大きな関数、モジュール、深いネスト。
2. 今回の実装にどのような機能要件上の「価値」があり、上で列挙された各「臭い」がどの「価値」の実装に属するかを記述する。
    + 「価値」とは **命令された要件や指示内容ではない** 。その機能や問題解決によって **ユーザが得られる利点** のこと。
3. 上で列挙した各「価値」ごとに、「検証」か「放置」かをタグ付けした表を出力する。表にはタグ付けの根拠として、以下リストにある全観点の **それぞれの分析結果を必ず記載** し、 1つでも該当したら「検証」判定とする。
    + 「価値」あたりの「臭い」の強さを考え、その臭いを提案報告に含めることが有益な場合、「検証」タグを付ける。
    + 「価値」とは指示内容ではないため、価値が不明な場合や指示内容をそのまま価値としている場合は「検証」タグを付ける。また当然、指示内容と比較しての評価、例えば、「指示内容を満たす最小実装だから良し」などは誤った判断でありその場合も「検証」タグを付ける。
    + 「価値は明確」「価値は自明」など何かしらの省略がされた場合は「検証」タグを付ける。
    + 実装を真似したコードが100箇所に増えた未来を仮定し、その未来において可読性が低い、または、場当たり的コードだらけになる場合は「検証」タグを付ける。仮定の話なので現状の話は正当化の根拠にならない。
4. 「検証」とタグ付けされた箇所について、現在案から独立した代案コードをサブエージェントに実装させる。サブエージェントは2つ走らせる。
    + 現在の実装方針や要件に引っ張られない多用な実装をさせるため、サブエージェントにはあなたの実装したコードだけを渡し、**機能要件や実装方針を一切与えない**。
    + 現在の環境の汚染を避けるため、サブエージェントにはあなたの実装したコードのsnapshotを渡す。サブエージェントにはその範囲外の書き換えを禁止する。
    + 現在案と重複した実装を避けるため、どのような「臭い」が問題になっているか、上記の「臭いリスト」の該当文を **そのまま渡し**、そしてそれを**避けて実装するよう指示する**。
5. 今回の実装と表示された代案のコードスニペットを出力し、良い方の実装例を採用する。その際、理由も出力する。
6. 「検証」タグがついたにもかかわらず現実装を維持した場合 **必ず**、その「臭い」がどの「価値」由来なのかを出力し、必ずユーザにその価値提供・仕様の再検討を提案しなければならない。
    + 例: 「POSIX shellでプロセス間ロックを実装しろとの指示を受けました。これは同時書き込みによるデータ破損を防ぎ安定性を向上させる価値のためのものだと推測されます。しかし、理解と保守には mkdir の原子性、kill -0、PID、signal trap、NFS などの専門知識が必要で複雑です。代案も検討しましたが、この複雑さを取り除けませんでした。今回は要求どおり実装しましたが、単一プロセスへの集約や専用ロック機構の利用など、他の仕様も選択可能だと考えます。」
