# レビューの知識を学習する

今回のセッションでユーザが指摘したことを、次回以降のレビュー (`my-review`) で使える知識として残す。

知識は、このスキルのディレクトリにある `knowledge/` に置く。

- `INDEX.md` — 知識の一覧。1 行が 1 つの知識。
- それ以外の `.md` — 知識の詳細。1 ファイルが 1 つの知識。

## 1. セッションから候補を拾う

今回のセッションを最初から振り返り、ユーザが以下をした箇所を拾う。

- あなたの成果物や提案を、指摘して直させた
- あなたの提案を、理由を添えて却下した
- 書き方や進め方の好みを述べた

拾うのは、**別のリポジトリの別の作業でも、同じ指摘が成り立つもの** だけにする。以下は拾わない。

- そのリポジトリだけで成り立つ決定 — そのリポジトリの文書に残すもので、ここに置くと他のリポジトリのレビューで誤った指摘になる
- その場かぎりの作業の指示
- レビューで確かめようのないもの — 成果物を見ても、守られたかどうかが分からないもの
- このセッションで既に学習の案として見せ、ユーザが退けたもの

## 2. 一般化する

候補を、今回の題材を知らない人が読んでも使える形に書き直す。
ユーザが言ったのは今回の対象についての一言であり、知識にするのは、その一言の背後にある判断の基準である。
理由が分からない候補は、推測で埋めずにユーザに尋ねる。

**知識は GitHub で公開される。プロジェクト固有の情報や社内の事情は、絶対に記録しない。**
一度公開されたものは、後から消しても取り消せない。以下は、詳細ファイルのどの節にも (例にも出所にも) 書かない。

- リポジトリ・人・組織・製品・顧客の名前
- 今回のコードや文章の現物
- 業務の内容、社内の体制や取り決め、未公開の計画

例は、同じ形をした別の題材で作る。出所は、何の仕事だったかが分からない言葉で書く。
伏せると知識として成り立たない候補は、記録せずに捨てる。

## 3. 既存の知識と突き合わせる

`INDEX.md` を最後まで読み、候補に近い行は詳細ファイルも読む。候補ごとに、以下のどれかに決める。

- **追加** — 近い知識が無い
- **更新** — 同じ知識が既にある。今回分かったこと (当てはまる条件、当てはまらない場合、例) を足す
- **置き換え** — 既存の知識と食い違う。どちらが今のユーザの考えかは、ユーザにしか分からない
- **変更なし** — 既存の知識が、今回の指摘を既に含んでいる。案に出さない

## 4. ユーザに案を見せる

書き込む前に、追加・更新・置き換えの候補の全部について以下を見せ、承認されたものだけを書き込む。

- 追加・更新・置き換えのどれか
- 索引の 1 行
- 詳細ファイルの全文 (更新と置き換えでは、変更前と変更後)

誤った知識は、以後のレビュー全部で誤った指摘を生む。ここでユーザが止められることが、それを防ぐ唯一の機会である。

見せる候補が無ければ、以下の一行だけを書いて終わる。

```
今回のセッションに、学習する指摘はありません。
```

## 5. 書き込む

詳細ファイルは、知識の内容を表す英小文字とハイフンの名前で作り、以下の形で書く。全部の節を書く。

```
# <知識の名前>

## 指摘すること

<レビューで何を見つけたら、何と指摘するか>

## 理由

<ユーザがそれを求める理由>

## 例

<反している例と、沿っている例>

## 当てはまらない場合

<一見当てはまるが、指摘してはいけない場合。分かっていなければ「未確認」と書く>

## 出所

<いつ、どんな場面でのどんな指摘から学んだか。日付と、一般化した言葉で>
```

`INDEX.md` には、知識 1 つにつき 1 行を書く。

```
- [<知識の名前>](<詳細ファイルの名前>) — <どんな対象をレビューするときに当てはまるか>
```

行の後半は、レビューする側がこの 1 行だけを見て、詳細を開くかどうかを決めるためのものである。
指摘の内容ではなく、当てはまる対象を書く。

最後に、追加・更新・置き換えたファイルの一覧を報告する。
